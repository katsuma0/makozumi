Security

What a Makozumi check proves — and what it does not

Makozumi is built on one idea: a code on a product carries a digital signature that only the issuer's private key could have produced, and anyone can check it without being able to produce one. Below is an honest account of every attack we could think of, what the system does about each, and the one attack that no static code can defeat.

What an ✓ AUTHENTIC result means

It means exactly this: the details shown on screen were signed by the holder of the Makozumi private key, and have not been altered by so much as one character since. It does not, by itself, prove that the physical object in your hand is the one the code was issued for — see cloning below.

Attacks and defences

AttackStatusHow
Invent a code for a fake product Stopped Requires the private key. Deriving it from the published public key is the elliptic curve discrete logarithm problem — about 2128 operations.
Edit a real code (change the owner, date, or item name) Stopped The signature covers every byte of the details. One changed character breaks the SHA-256 hash and verification fails.
Sign a code with the attacker's own key Stopped Verification uses only the public keys published in this site, selected by a key id that must be one we recognise.
Strip the signature, or claim "no algorithm" Stopped The algorithm, curve, and hash are fixed in the verifier's code. A code cannot choose them, so the classic alg:none token attack does not exist here.
Reuse a valid signature on different details Stopped The signature is checked against the exact payload it accompanies, not against any part of it.
Hostile content inside a code (scripts, hidden text, reversed text) Stopped Nothing is displayed before the signature verifies; all values are written as plain text, never as markup; control and text-direction characters are stripped; field lengths are capped.
Oversized or malformed code to crash the checker Stopped Length, character set, and signature size are validated before parsing. Any failure shows a clear negative result rather than an error.
Rewrite the NFC chip to point at a lookalike site Stopped, if you lock the tag Lock or password-protect the chip after writing (see below). The verifier also shows the exact site address at the top of every check, so a lookalike domain is visible.
Embed the real verifier in a fake page to fake a result Stopped The page refuses to run inside a frame, and its content security policy forbids framing and all third-party code.
Tamper with the verifier in transit Stopped The site is served over HTTPS only; a plain-http visit is redirected. The page loads no external scripts, fonts, or trackers, so there is no third party to compromise.
Keep using a code after the item is lost or stolen Stopped Its serial is added to the published revocation list, and the checker then reports REVOKED even though the signature is still valid.
Use a stolen private key indefinitely Contained Every code names the key that signed it. A compromised key is retired, a new one published, and codes signed by the old key can be revoked in bulk.
Copy a genuine code onto another item Not stopped See the section below. This is the real limit of the system.

The one attack cryptography cannot stop

A Makozumi code is a fixed string. Anyone who can read a genuine tag — a customer, a courier, anyone who handles the product — can copy that string and write it to a second chip. Both chips will then verify, because both carry a genuinely signed code. No signature scheme can prevent this, because the copy is not a forgery; it is the original.

What limits the damage today:

  • Every code carries a unique serial number, shown on every check. Two items bearing the same serial means one of them is a copy.
  • A serial known to be copied can be revoked, which kills every copy of it at once.
  • The chip should be physically fixed to the item so that removing it destroys it.

The proper fix, when it is worth the cost

Chips such as the NTAG 424 DNA compute a fresh cryptographic code on every single tap, using a secret held inside the chip that cannot be read out. A copied string is then useless, because it was only valid for one tap. Checking those codes requires a small server that remembers each chip's tap counter, so it no longer fits on a purely static site — but the design here upgrades to it without changing anything a customer sees.

Operating rules that keep this safe

  1. The private key never leaves your own machine. It is not in this repository and must never be committed, emailed, or pasted into any site other than the local generator page.
  2. Back the key up. Lose it and no new codes can ever be issued under the current key.
  3. Lock every chip after writing it. In NFC Tools, use "Lock tag" or set a password. An unlocked chip can be rewritten by anyone who can touch it, which is the easiest real-world attack on this system.
  4. Use a fresh serial number for every item. Serials are what make copies detectable.
  5. Publish only one official address and put it on your packaging, so customers know what the real one looks like.
  6. If a key is ever exposed, retire it in the verifier, publish a new key, and revoke the affected serials.

Reporting a problem

If you find a tag that behaves oddly, two items with the same serial, or a website impersonating this one, contact the issuer named on the code before trusting the item.
